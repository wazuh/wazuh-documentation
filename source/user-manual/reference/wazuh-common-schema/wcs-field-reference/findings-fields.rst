Findings fields
===============

The findings data streams store findings generated by detection rules. Wazuh creates one data stream for each event category, for example ``wazuh-findings-v5-security`` and ``wazuh-findings-v5-system-activity``. You can query all of them with the ``wazuh-findings-v5*`` index pattern.

Findings include all the :doc:`event fields <event-fields>`, plus fields that describe the rule that matched and the case the finding belongs to:

-  ``wazuh.rule.*``: The rule that generated the finding, including its ID, title, level, and status, its MITRE ATT&CK mapping (``wazuh.rule.mitre.*``), its compliance requirements (``wazuh.rule.compliance.*``), and the Sigma rule it was imported from (``wazuh.rule.sigma_id``).
-  ``wazuh.case.*``: The case the finding is attached to, including its title, status, severity, priority, TLP classification, owner, and comments.
-  ``event.doc_id`` and ``event.index``: The ID and the backing index of the event that matched the rule.

The complete list of findings fields is in the `fields.csv <https://github.com/wazuh/wazuh-indexer-plugins/blob/|WCS_REF|/wcs/stateless/events/findings/docs/fields.csv>`__ and `wcs_flat.yml <https://github.com/wazuh/wazuh-indexer-plugins/blob/|WCS_REF|/wcs/stateless/events/findings/docs/wcs_flat.yml>`__ files of the ``stateless/events/findings`` module.

Example: Set the level of a finding from a rule
-----------------------------------------------

Decoders don't write findings fields. Wazuh creates a finding when an event matches a rule, and copies the rule's details into ``wazuh.rule.*``. ``wazuh.rule.level`` comes from the rule's ``level``. This rule matches the failed SSH logins that the ``system-auth`` integration decodes from the authentication log of a Linux endpoint.

Create the rule in **Ruleset management** > **Detection** > **Rules**. ``logsource.product`` names the integration whose events the rule evaluates. The events come from a built-in integration, so add the rule to a custom integration whose title is the same as the built-in one, for example ``wazuh-fim``. Then promote it to the custom space and add it to a custom detector in **Ruleset management** > **Detection** > **Detectors**. The highlighted lines show where ``wazuh.rule.level`` is used and where it appears in the output.

**Rule**

.. code-block:: yaml
   :emphasize-lines: 3

   logsource:
     product: system-auth
   level: high
   status: experimental
   enabled: true
   tags:
     - attack.credential-access
     - attack.t1110
   detection:
     condition: selection
     selection:
       event.dataset: system-auth
       event.outcome: failure
   metadata:
     title: SSH authentication failure
     author: Security Team
     description: Detects a failed SSH authentication on a monitored endpoint.

**Finding (excerpt)**

.. code-block:: json
   :emphasize-lines: 17

   {
     "_index": ".ds-wazuh-findings-v5-system-activity-000001",
     "_source": {
       "event": {
         "dataset": "system-auth",
         "action": "connection-closed",
         "outcome": "failure",
         "doc_id": "ncvwq6EBmx_Zvxl5lghO",
         "index": ".ds-wazuh-events-v5-system-activity-000001"
       },
       "user": { "name": "wcsdocsfail" },
       "source": { "ip": "192.168.72.3" },
       "wazuh": {
         "agent": { "name": "Ubuntu" },
         "rule": {
           "title": "SSH authentication failure",
           "level": "high",
           "tags": [ "high", "system-auth", "attack.credential-access", "attack.t1110" ]
         }
       }
     }
   }

.. note::

   -  Filter findings by ``wazuh.rule.level`` to triage the most severe ones first.
   -  The rule level is also the first item of ``wazuh.rule.tags``, followed by the integration and the rule's own tags.
   -  ``event.doc_id`` and ``event.index`` point to the original event in the events data stream.
