Log data analysis
===================

Log data analysis involves collecting and analyzing logs generated by applications, network devices, endpoints, and cloud services to gain visibility into an IT environment. This visibility supports a range of security and operational use cases, including threat detection, performance monitoring, troubleshooting, compliance auditing, and identifying anomalous activity.

In Wazuh 5.0, log data analysis consists of the following stages:

-  Log collection: Collecting logs from monitored endpoints, applications, network devices, and cloud services.
-  Normalization, decoding, and enrichment: Processing collected events and converting them to the Wazuh Common Schema (WCS).
-  Rule matching and findings visualization: Analyzing events against detection rules and presenting the resulting findings in the Wazuh dashboard.

Wazuh Log Test
----------------

The Wazuh log test tool matches logs against the detection content of your deployment. It helps when writing and debugging custom decoders, rules, and KVDBs. Log test evaluates the rules of the integration that you select under **Detection**. Without an integration, it normalizes the event and skips detection.

Navigate to **Ruleset management** > **Log test** in the Wazuh dashboard. Select **Standard** in the space selector. Under **Detection**, select **normalized-threats** in **Integration**. Paste the following sample log in **Log event**, then click **Test**:

Normalization, decoding, and enrichment
-----------------------------------------

In the decoding phase, the Wazuh normalization engine on the Wazuh manager uses decoders and KVDBs to normalize, enrich, and match incoming log data. For example, the following decoders match the above log sample:

-  ``"decoder/core-wazuh-message/0"``
-  ``"decoder/windows-event/0"``
-  ``"decoder/windows-defender/0"``

The ``"decoder/core-wazuh-message/0"`` decoder matches the full event, while the ``decoder/windows-event/0`` decoder matches the type of event. The ``decoder/windows-defender/0`` decoder normalizes the rest of the event; however, this event does not include enrichment data.

To view a decoder, go to **Ruleset management** > **Decoders** and search for its name, for example, ``decoder/windows-defender/0``.

Rule matching and findings visualization
-------------------------------------------

In this phase, detectors in the Wazuh indexer compare normalized events against the rules and generate findings. Each finding combines the matched rule metadata with the normalized event data, providing the context needed to investigate the activity. In the Wazuh dashboard, analysts filter for related findings during triage and can review affected assets, event fields, ATT&CK mappings, and compliance information.

By default, detectors generate findings for rules of every level: ``informational``, ``low``, ``medium``, ``high``, and ``critical``. In this scenario, the log triggers a ``High`` finding.

In the **Log test** result, click the **Detection** tab, then click the rule title, **Malware file detected - {{file.path}}**, to view its details. To open the rule on the **Rules** page, click **View this rule**.

On the **Rules** page, click the **View rule details** icon in the **Actions** column of the rule, then click **YAML** in the **Rule details** flyout:

.. code-block:: yaml

   id: e042f947-36a0-578d-9fa9-98cf65b35f95
   logsource:
     product: normalized-threats
     category: malware
   tags:
     - attack.execution
     - attack.impact
     - attack.t1204
     - attack.t1059
   falsepositives:
     - >-
       Security research and controlled malware analysis environments; exclude them
       by host.name together with the analysis folder in file.path
     - >-
       Antivirus test files (EICAR) used to check that protection works; exclude
       the test by file.name together with the test host.name
   level: high
   status: stable
   enabled: true
   detection:
     condition: >-
       selection and not filter_rootcheck and not
       filter_asr_vulnerable_driver_block and filter_has_path
     filter_asr_vulnerable_driver_block:
       event.code: '1121'
       event.dataset: defender
       rule.id: 56A863A9-875E-4185-98A7-B882C64B5CE5
       wazuh.protocol.location: EventChannel
     filter_has_path:
       file.path: '*'
     filter_rootcheck:
       wazuh.integration.name: wazuh-rootcheck
     selection:
       event.action:
         - malware-detected
         - malware-quarantined
         - malware-blocked
         - malware-cleaned
       event.category|contains: malware
   metadata:
     title: Malware file detected - {{file.path}}
     author: Wazuh, Inc.
     description: >
       Detects when malware, ransomware, or other malicious software is identified
       on a host and the affected file path is known. Covers detection, quarantine,
       blocking, and cleaning actions from EDR, AV, and EPP platforms. Immediate
       investigation is required to determine scope and prevent lateral spread.
     references:
       - https://attack.mitre.org/techniques/T1204/
       - https://attack.mitre.org/techniques/T1059/
     documentation: >-
       Investigate: confirm the file in file.path and the detection name the source
       gives (rule.name, threat.software.name or threat.indicator.name). Check
       which process and user wrote or ran the file, whether the product removed,
       blocked or only reported it (event.action), and look for the same file name
       or hash on other hosts. A detection inside a malware analysis or security
       test folder is the usual benign case.


       Blind spots: A source whose decoder writes no file.path is not seen
       (filter_has_path), and neither is an event whose category is not malware or
       whose action is not one of the four listed. Wazuh rootcheck findings are
       excluded (filter_rootcheck): rootcheck rules read them. Microsoft Defender
       ASR blocks (event 1121) of the ASR rule Block abuse of exploited vulnerable
       signed drivers (56A863A9-875E-4185-98A7-B882C64B5CE5) are excluded
       (filter_asr_vulnerable_driver_block): a known vulnerable signed driver is
       not malware, and that block belongs to a dedicated windows-defender rule at
       T1068 (precedent P24). The exclusion matches the ASR rule GUID as Defender
       writes it, in uppercase; every other ASR rule GUID and every other Defender
       event keeps this finding.
     supports:
       - ''
     modified: '2026-11-19'
   mitre:
     tactic:
       id:
         - TA0002
         - TA0040
       name:
         - Execution
         - Impact
     technique:
       id:
         - T1204
         - T1059
       name:
         - User Execution
         - Command and Scripting Interpreter
   compliance:
     fedramp:
       - SI-3
     gdpr:
       - Article 32
       - Article 33
       - Article 5
     hipaa:
       - 164.308(a)(5)(ii)(B)
     nis2:
       - IR-6.9

       - SI-3

       - 5.2.2

       - CC6.8
