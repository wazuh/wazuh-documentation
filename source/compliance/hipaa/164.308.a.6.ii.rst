HIPAA § 164.308(a)(6)(ii) - Response and reporting
======================================================

The HIPAA § 164.308(a)(6)(ii) requirement states, "*Identify and respond to suspected or known security incidents; mitigate, to the extent practicable, harmful effects of security incidents that are known to the covered entity or business associate; and document security incidents and their outcomes.*"

This requirement mandates identifying suspected or known security incidents, responding to them, mitigating their potential impact, and documenting the incidents and their outcomes.

Wazuh helps meet this requirement by providing several security monitoring and incident response modules. One of these modules is the Wazuh :doc:`Active Response </user-manual/capabilities/active-response/index>` module, which automates response actions when security findings meet configured conditions. Wazuh Active Response can execute predefined or custom scripts on monitored endpoints to mitigate detected threats. For example, it can block malicious IP addresses, terminate malicious processes, or perform other configured response actions when a security finding triggers an active response.

Use case: Block a web attack with active response
-----------------------------------------------------

In this use case, Wazuh detects a Cross-Site Scripting (XSS) attack on an Apache web server that runs on a monitored Ubuntu 24.04 endpoint. An active response then blocks the IP address of the attacker. You need a second endpoint with HTTP access to the web server to run the attack.

Ubuntu endpoint
^^^^^^^^^^^^^^^^

Perform the following steps to install an Apache web server and monitor its logs with the Wazuh agent.

#. Update local packages and install the Apache web server:

   .. code-block:: console

      $ sudo apt update
      $ sudo apt install apache2

#. If a firewall is enabled, allow external access to web ports:

   .. code-block:: console

      $ sudo ufw app list
      $ sudo ufw allow 'Apache'
      $ sudo ufw status

#. Check that the Apache web server is running:

   .. code-block:: console

      $ sudo systemctl status apache2

#. Add the following configuration to the Wazuh agent ``/var/ossec/etc/ossec.conf`` file to monitor the Apache access log:

   .. code-block:: xml

      <localfile>
         <log_format>syslog</log_format>
         <location>/var/log/apache2/access.log</location>
      </localfile>

#. Restart the Wazuh agent to apply the changes:

   .. code-block:: console

      $ sudo systemctl restart wazuh-agent

Wazuh dashboard
^^^^^^^^^^^^^^^^

#. Open the menu (☰) and go to **Explore** > **Active Responses**.

#. Click **Create active response** and fill in the form with the following values. The ``block-ip`` executable adds firewall rules that drop traffic from the source IP address of the finding. The **Local** location runs it on the endpoint that generated the finding. The **Stateless** type runs it once and never reverts it.

   | Field      | Value         |
   +============+===============+
   | Name       | web_attack_ar |
   +------------+---------------+
   | Executable | block-ip      |
   +------------+---------------+
   | Location   | Local         |
   +------------+---------------+
   | Type       | Stateless     |
   +------------+---------------+

Attack emulation
^^^^^^^^^^^^^^^^^^

Perform the following steps from the second endpoint.

#. Replace ``<WEBSERVER_IP_ADDRESS>`` with the IP address of the Ubuntu endpoint and run the following command:

   .. code-block:: console

      $ curl -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36" "http://<WEBSERVER_IP_ADDRESS>/index.html?q=<script>document.cookie</script>"

   The first request reaches the web server. It generates a web attack finding, which triggers the ``block-ip`` active response.

#. Wait three minutes, then run the command again to confirm that the Ubuntu endpoint blocks the attacker:

   .. code-block:: console

      $ curl -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36" "http://<WEBSERVER_IP_ADDRESS>/index.html?q=<script>document.cookie</script>"

   The command output looks similar to this:

   .. code-block:: none
      :class: output

      curl: (28) Failed to connect to <WEBSERVER_IP_ADDRESS> port 80 after 134781 ms: Couldn't connect to server

   On the Ubuntu endpoint, run ``sudo iptables -S INPUT | grep <ATTACKER_IP>`` to check the block. Replace ``<ATTACKER_IP>`` with the IP address of the attacker endpoint. The output shows the DROP rule that the active response added.

After the test, remove the firewall rules on the Ubuntu endpoint. The active response is stateless, so it never removes them:

.. code-block:: console

   $ sudo iptables -D INPUT -s <ATTACKER_IP> -j DROP
   $ sudo iptables -D FORWARD -s <ATTACKER_IP> -j DROP
